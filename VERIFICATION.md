# Release verification

Version 3.1.5, prepared 2026-11-01.

Following the user's explicit request to use maximum building speed, 3.1.5 adds Max as the initial speed selection. Max uses the existing 600-request/s and 64-pending ceilings from the start, without latency-based growth or reductions, and expands placement/resize groups to the existing 300-job window size. It shares the Luau.pro preparation method but preserves its separate limits. Painting stays serial at 32 models per call. The shared admission gate, ownership matching, first-block proof, cancellation/manual drains, request timeout, pending locks and final geometry/color checks remain active. Standard Luau.pro and Rapid retain adaptive behavior; Compatible maps Max to Fast. No live build is hot-patched or replayed by publication.

The ongoing 3.1.4 run passed 6,301 verified blocks, beyond the earlier color failure, but its running average at 262.59 wall seconds was about 24 blocks/s with nine workers. That is a partial-run observation, not completed-run validation. Max is a separate fixed-budget choice in response to the user's request; its live performance remains unverified until a new run.

At 60 simulated FPS with 180 ms replies, a 1,201-block deterministic comparison took 33.20 seconds in the preserved 3.1.4 Luau.pro mode and 18.00 seconds in Max. With every 503rd reply taking 1.65 seconds, the same comparison took 37.933 and 22.300 seconds. Both verified all blocks with 2,443 requests and only one paint call active. Max reached but did not exceed 64 pending wall requests. These are local simulations, not a guaranteed game speed.

The live 3.1.3 test caught a regression in overlapping paint: 301 blocks were identified, but verification stopped after 65 completed blocks because color was wrong despite exact geometry. All calls had returned; the color check waited eight seconds. This supports reverting concurrent paint, but does not prove the server's internal cause. Version 3.1.4 restores serial 32-model paint batches and retains the 3.1.3 latency controller. It introduces no automatic repaint, retry, deletion or partial-build resume. A mock that rejects overlapping paint now verifies the serial path. Final wall-only RPC counts and mean latency exclude preparation.

The same live test verified preparation in that session: available PlasticBlock rose from 14,479 to 28,438.2529 after 141 scale calls, and the helper was removed. This is observed client-side inventory evidence for that attempt, not a completed image or a guarantee across sessions.

A comparable serial-paint mock isolates the retained controller change: 1,201 blocks, 60 simulated FPS, normal 180 ms replies with every 503rd reply delayed to 1.65 seconds. Original 3.1.1 took 62.033 seconds and 3.1.4 took 37.933 seconds. Both verified all 1,201 blocks with 2,443 requests and at most one paint request outstanding. This is 38.8% less simulated elapsed time, not measured live throughput.

The user reported 22.7 blocks/s at 308 seconds in 3.1.1. A later local report confirmed that the attempt stopped with 14,551 of 28,232 blocks verified in 707.485 seconds (20.567 verified blocks/s), with 14,701 blocks identified. Inventory was already sufficient, so no preparation calls occurred in this attempt and it provides no evidence about new material gain. The earlier running display included preparation time in general, but that was not the cause of this run's measured slowness.

The report recorded 29,844 completed RPCs averaging 0.1814 seconds, a 1.6481-second maximum, 58 admission reductions and 110 increases. Final EWMA was 0.1048 seconds with only eight workers. These aggregate data motivated testing the controller's sensitivity to brief latency spikes; they do not establish the timing distribution of every reply. The 3.1.3 Luau.pro-only correction requires a majority of slow replies in the latest 16 samples, with at least three samples, before ordinary backoff. A single severe reply of at least four seconds still reduces admission. A two-second reduction cooldown prevents repeatedly halving capacity for one delayed group. Growth retains healthy-reply requirements and its three-second cadence. Global ceilings, timeouts, Rapid and preparation are unchanged.

In deterministic 1,201-block comparisons at 60 simulated FPS, 180 ms replies with every 503rd reply delayed to 1.65 seconds took 58.23 seconds under 3.1.2 and 32.47 seconds under 3.1.3. Constant 180 ms replies remained 27.93 seconds in both. At 30 FPS, the corresponding sparse-delay run improved from 60.73 to 33.57 seconds. These are constructed latency patterns for regression testing, not a replay of every live response. Sustained slowness, load-dependent latency, correlated delayed replies and a severe reply still trigger reductions in the tests.

The earlier 3.1.2 change allowed four disjoint paint batches to share the admission controller. That experimental scheduling is reverted in 3.1.4 after the live failure above. Placement identification, the first-block proof, final verification and material preparation are retained. Periodic progress still separates wall time from preparation, and a bounded local live-progress file makes the current phase and timings inspectable without waiting for completion. The version shown in the interface matches the release.

Historical local mock runs compared 3.1.1 with two- and four-batch candidates at 30/60 simulated FPS and 100/350 ms RPC delay. At 60 FPS and 350 ms delay, 1,201 blocks took 52.20 seconds with serial paint, 45.00 seconds with two batches and 42.63 seconds with four. Requests and verified counts were unchanged in those mocks. Those results did not establish game compatibility and do not describe the restored serial-paint release.

The reported live 3.1.0 attempt never reached image placement: it needed 141,015 material, began and ended with 14,479, and completed 187 preparation scale calls before cancellation. Its first estimated round had 1,279 calls, but the UI showed no progress within that round. This establishes zero net gain for that attempt, not failure of the original Luau.pro method; the user reports that the original still works.

The 3.1.1 correction restores simultaneous dispatch within each preparation group, adds progress while requests are pending, measures net gain before extending the first group, and separates helper refunds from material gains. The original can overlap groups without joining every callback; this adapter deliberately tracks and drains each group, with at most 100 preparation requests pending. Wall dispatch now adapts to response latency. Local timing simulations can verify these scheduling and lifecycle properties; they do not establish the current game's material response.

The 3.1.0 image-builder update adds a Luau.pro profile to the independent game adapter. It ports shared-helper material top-ups and staged placement, paint and resize from the recovered source descriptions. The original Luau.pro VM, factory and unresolved authorizer/reconciler are not executed or included. The prior Rapid, Turbo, Fast and Normal paths remain available. The AI builder is outside this release.

The new profile retains ownership matching, real inventory checks, bounded request concurrency, cancellation, cleanup, tool restoration and final geometry/color verification. Local simulations cover the port; they are not a live server throughput or inventory measurement.

The 3.0.1 compatibility update uses executor-relative paths throughout, tests HTTP aliases by function capability, accepts numeric HTTP status variants, and verifies workspace write/read access even when `isfolder` is missing. Tests simulate different workspace roots; they do not certify a particular executor or mobile platform. A small `workspace-check.txt` file is removed after a successful probe when `delfile` is available.

The release is built from the public source tree. It includes all PNG and JPEG license notices inside the downloaded bundle as well as in the repository. A publish allowlist and local scan exclude private pairing tokens, personal Windows paths, generated private loaders, local server configuration, recorder data, and recovered third-party scripts.

Automated checks run with the official Luau CLI and Python/Pillow:

- Complete bundled client, adapter, planner, decoder and loader syntax/compilation.
- 179 simulated adapter scenarios. Nine Max cases cover 300-block nil-return matching, existing/manual object preservation, fixed slow-reply behavior, ambiguity rejection, cancellation, late locks, manual selection and unchanged preparation. Earlier coverage includes serial paint order, overlap-rejecting paint mocks, prep-excluded wall metrics, periodic progress and adaptive congestion handling. Phase order, ownership and final geometry/color checks remain covered. These use local doubles and send no live game requests.
- 34 interface logic scenarios covering options, placement rotation/origin, cancellation, progress, reload behavior, normal hotbar selection, the new default, live material counters, wall-only elapsed time and bounded local diagnostics. Terminal snapshots distinguish complete, stopped and unverified outcomes.
- 34 PNG/wrapper cases, including color types, filters, interlacing, checksums, malformed files, memory bounds, cancellation, and independently verified preview PNG output.
- 14 JPEG test methods using synthetic Pillow fixtures: baseline/progressive, grayscale/RGB, subsampling, odd dimensions, restart markers, EXIF orientations 1–8, malformed data, scan/table limits, cancellation and cooperative yielding. Lossy output is checked with appropriate tolerance; it is not claimed identical to libjpeg's chroma smoothing.
- 26 planner scenarios, including exact Source RGB, 250,000-cell plans, alpha-aware filters, palettes, non-overlapping rectangle reconstruction, transparency, preview bounds, cancellation and work limits.
- Loader success/failure checks for manifest/path validation, HTTP failures, compile errors, cache write/readback failure, runtime startup failure, and concurrent launch suppression.
- Backend checks for download errors/limits, cancellation, credential-bearing URL rejection, local diagnostics, and nonfatal preview failure. Live progress is throttled, drops unknown/nonfinite fields, marks run completion, and does not overwrite the previous completed-run report.
- 11 preview-cache cases covering journal/path validation, three-file bounds, stale jobs, missing files, deletion failures, readback mismatches, and partial writes.
- Two complete real-code conversion fixtures: RGBA PNG and an EXIF-rotated progressive JPEG, from mocked HTTP response to plan and encoded preview.

The bundled standalone release has not yet been verified inside a live Wave/Roblox session. CLI tests do not prove an executor's API compatibility, native image display, current game protocol, inventory outcomes, or a guaranteed build rate. The builder retains live verification and stops if the game does not confirm its changes.

The private PC-server test version remains separate from this public package.
